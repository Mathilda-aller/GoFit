# 「练过」四人团队分工与协作约定

> 适用于本次黑客松。本文只说明每个人负责哪一部分、要实现什么结果、最终交付什么，以及四个人怎样把成果接在一起。具体技术方案由负责人自行探索，但不能改变本文约定的产品边界和数据接口。

## 1. 全员共同目标

四个人共同交付一条可以连续演示的 P0 主流程：

```text
视频接入
  → AI 生成忠于原视频的视频动作卡
  → 用户手动加入练单
  → AI 练单助手给出不超过 3 个候选和理由
  → 用户开始训练并记录体感
  → 有发力问题时查看同动作、跨视频的练友经验
  → 本次体感影响下次推荐
```

必须始终区分三个对象：

- **视频动作卡**：只整理一条来源视频明确表达的内容。用户收藏、加入练单和训练时使用的是它。
- **标准动作**：后台关联节点，用于连接同一个动作的不同视频、评论和反馈；P0 不做独立动作百科页。
- **练友经验**：AI 对同一标准动作下的多条公开评论进行整理，并保留原评论和原视频来源；它不是当前视频作者的观点，也不是专业诊断。

任何模块都不能把其他视频或评论中的内容写进当前视频动作卡，也不能让 AI 自动替用户修改练单。

## 2. 四人分工总览

| 角色 | 负责的产品部分 | 最终要证明的结果 |
| --- | --- | --- |
| 前端 A：设计与体验 | 视觉、页面结构、主流程体验、通用组件 | 整个 Demo 看起来和用起来像同一个完整产品 |
| 前端 B：交互与数据呈现 | 前端状态、复杂交互、肌群图、模拟数据 | 用模拟数据交付可以完整点击的 Demo |
| AI 后端：AI 能力与推荐 | 视频重构、动作归一、评论聚类、动作推荐 | AI 的三项核心能力真实运行、结果可解释且可追溯 |
| 业务后端：数据与系统闭环 | 数据库、业务规则、对外 API、任务编排、部署 | 公共内容和个人数据稳定流转，完整主流程可以连续跑通 |

分工代表结果责任，不代表只能修改自己目录。联调时可以互相补位，但某项结果出现问题时，由表中对应负责人牵头解决。

## 3. 前端 A：设计与体验

### 负责范围

负责把 PRD 和交互说明转化为统一、可理解的移动端体验，重点覆盖视频接入与处理、视频动作卡、练单编辑、动作选择与推荐、训练执行、体感反馈、练友经验、安全提示、训练完成和“我的”。

这一角色要决定页面的信息层级、视觉风格和操作反馈，并维护按钮、标签、卡片、抽屉、加载、空状态、错误提示、来源标签等通用组件的一致性。设计不只覆盖正常页面，也要让用户看得懂处理中、失败、数据不足、网络异常和不适分流等状态。

设计稳定后，继续负责主要页面和通用组件的前端实现，确保最终代码与设计一致，并适合手机尺寸连续演示。

### 要实现的结果

- 用户不需要解释就能看懂“原视频内容”“AI 整理”和“练友经验”的区别。
- 收藏、加入练单、开始训练三个动作不会混淆；AI 推荐始终等待用户确认。
- 用户在训练现场能快速查看动作暗号、示范片段和当前进度。
- 普通发力问题进入练友经验，不适、疼痛等风险进入独立安全提示。
- 所有主流程页面在视觉和交互上保持一致，返回后能回到合理位置。

### 交付成果

- 一份覆盖 P0 主流程和关键异常状态的原型；
- 视觉规范与可复用前端组件；
- 自己负责页面的可运行代码；
- 可在手机尺寸连续演示的完整界面。

## 4. 前端 B：交互与数据呈现

### 负责范围

负责前端的数据状态和较复杂的交互实现，包括动作卡数据展示、练单增删与排序、推荐候选刷新、训练进度与恢复、体感提交、练友经验展开、训练总结，以及人体肌群和健身搭子的点亮效果。

使用一套集中管理的模拟数据让前端 Demo 独立跑通。页面组件不能到处写死数据，而应从统一的数据入口读取；同时说明每个页面需要什么数据、用户操作后期望发生什么变化，方便业务后端在不重写页面的情况下接入真实接口。人体 SVG、图标和媒体素材也由这一角色整理，肌肉路径使用双方确认的统一编号，不能靠中文名称临时匹配。

### 要实现的结果

- 练单的加入、删除、排序和保存状态准确，刷新或返回页面后不会无故丢失。
- 从练单创建的“本次训练”是独立记录，训练进度和体感不会反向修改原练单。
- 推荐加入、不感兴趣、体感提交和查看练友经验都会触发正确的页面与数据变化。
- 肌群图能够根据单个动作和整份练单的数据正确点亮，并区分主要与辅助肌群。
- 模拟数据集中存放，后端接入真实数据时不需要改动页面结构和业务组件。

### 交付成果

- 一套集中管理的前端 Demo 数据与素材；
- 可独立点亮的正反面肌群 SVG 和健身搭子素材；
- 练单、训练、反馈、推荐和肌群联动代码；
- 清楚的数据入口和页面数据需求说明；
- 一个不依赖后端也能完整点击演示的移动端 Demo。

## 5. AI 后端：AI 能力与动作推荐

### 负责范围

AI 后端负责三项能力，它们都需要有稳定输入输出、可独立运行，并能由业务后端调用。

#### 1. 视频重构与动作卡生成

完成视频的 ASR、OCR、VLM 理解、时间对齐、标准动作匹配、动作知识提取、来源校验和媒体片段选择，并封装为 `FitnessVideoToActionCardSkill`。生成的步骤、要点、错误提示和动作暗号必须能回到原视频证据；原视频没有表达的内容不能补写。VLM 负责判断画面和候选时间，FFmpeg 负责准确输出封面及循环短视频。

#### 2. 评论聚类与问题匹配

将同一标准动作下的公开评论按问题和方法整理，输出摘要、提及条数、不同意见、适用条件、风险标记和原回答 ID，并封装为 `PeerExperienceDigestSkill`。评论聚类主要在素材导入或评论更新时提前生成；用户反馈后，系统只按“标准动作 + 问题标签”召回已有结果，不为每次反馈重新分析全部评论。样本不足时展示原评论，不制造确定结论；遇到疼痛、麻木、眩晕或危险建议时进入安全分流。

#### 3. 练单助手的动作推荐

AI 后端同时负责推荐能力的实现，包括候选过滤、规则排序、去重、最多返回 3 个候选、选择推荐原因，以及生成一句用户能理解的理由。推荐需要综合当前练单、身体大区与具体肌群、收藏、历史体感、不感兴趣和不适记录。

P0 的推荐是可解释的结构化规则，不是让大模型自由制定训练计划。程序决定候选和顺序；理由优先使用审核过的模板，LLM 如参与只能润色已确定的原因，不能更换候选、修改排序或自动加入练单。曾记录不适、来源存在风险或关键信息不完整的动作不得主动推荐。

### 要实现的结果

- 一条主 Demo 视频可以真实生成可追溯的视频动作卡，并有稳定的备份结果。
- 多条同动作评论可以整理成有来源、有分歧、有风险标记的练友经验。
- 推荐会随着当前练单和历史体感变化，结果不超过 3 个，每个候选只有一个主要理由。
- 三项 AI 能力均可单独测试，失败时返回明确状态，不把内部 prompt 或异常直接暴露给前端。

### 交付成果

- 可运行的视频重构 Workflow、动作卡 Skill 和媒体产物；
- 可运行的评论聚类 Skill、一组真实聚类结果及安全识别结果；
- 可运行的推荐模块、规则版本、原因编码和测试样例；
- 三项能力的输入输出说明、成功示例、失败示例和调用方式；
- 可用于路演展示的 AI 运行记录和备份数据。

## 6. 业务后端：数据与系统闭环

### 负责范围

业务后端拥有系统中的业务事实和对外接口，包括来源视频与处理任务、公共视频动作卡、标准动作、收藏、练单、训练会话、体感、推荐事件、公开评论与练友经验、用户身份和安全记录。

它负责数据库、权限、幂等、状态恢复和 Demo 数据初始化，并向前端提供唯一的一套业务 API。前端完成可交互 Demo 后，由业务后端接管前端统一的数据入口，用真实接口替换模拟数据；接入时不随意修改已经确认的页面结构和交互。

它还负责任务编排：接收视频后创建处理任务，调用 AI 后端，校验返回结构并保存动作卡；评论更新时触发聚类并保存结果；请求推荐时准备推荐所需的业务上下文，调用 AI 推荐模块，再记录曝光、加入和不感兴趣等事件。

业务后端不负责设计 prompt、动作识别、聚类算法或推荐排序，但必须保证传给 AI 的数据正确，并在结果入库前检查 ID、来源、权限和安全约束。它也不能用 AI 结果绕过用户确认去修改练单。

### 要实现的结果

- 同一来源视频只对应一张公共基础卡；重复请求不会生成重复数据。
- 练单、训练会话和体感彼此边界清楚，刷新、重复点击和中途退出不会破坏记录。
- 前端只连接业务 API，就能完成视频处理查询、动作卡、练单、训练、反馈、推荐和练友经验全流程。
- 前端原有的模拟数据可以被真实接口替换，接入后不破坏已经确认的页面和交互。
- AI 任务可以异步执行、查询进度、失败重试或使用备份结果，不阻塞普通业务请求。
- 公共内容和个人数据分开保存；未主动公开的训练体感不会进入公共经验池。

### 交付成果

- 数据库结构、迁移和固定 ID 的 Demo 种子数据；
- P0 所需的业务 API 及接口文档；
- 对前端数据入口的真实接口接入；
- AI 任务编排、结果校验、保存和状态查询；
- 身份、权限、幂等、训练恢复和安全分流；
- 全员可访问的测试环境、数据重置能力和最终部署。

## 7. 统一架构与仓库约定

### 7.1 使用一个 GitHub 单仓库

四个人共同使用 [Mathilda-aller/GoFit](https://github.com/Mathilda-aller/GoFit)。仓库一级目录直接按团队责任分成 `frontend` 和 `backend`，让每个人一眼知道自己的主要工作放在哪里：

```text
frontend/
  src/                    # 页面、组件、交互和统一数据入口
  mock-data/              # 前端可交互 Demo 使用的模拟数据
  assets/                 # SVG、图片和演示媒体
  README.md               # Demo 启动方式和数据替换说明

backend/
  business/               # 业务 API、数据库访问、任务编排和前端接口接入
  ai/                     # 视频重构、评论聚类、动作推荐和媒体处理
  database/               # 数据库迁移和固定 Demo 数据
  README.md               # 后端整体启动与联调说明

docs/
  api.md                  # 前端需要的接口，由业务后端维护
  demo-flow.md            # 四个人共同确认的演示路径
  deployment.md           # 启动和部署说明
```
前后端交接需要的内容直接写进 `docs/api.md`，AI 后端和业务后端之间的内部输入输出写进 `backend/ai/README.md`。这些文档只记录双方怎样连接，不要求大家维护一套复杂的共享代码。

目录表达责任边界，不限制具体框架。AI/媒体处理应保持独立任务，避免在普通网页请求中同步执行长时间的 ASR、模型调用和转码。

### 7.2 前端只对接业务后端

```text
前端可交互 Demo
   ↓ 由业务后端接入真实 API
业务后端（前端唯一连接对象）
   ├─ 读写数据库、权限与状态
   ├─ 调用 AI 推荐，返回最多 3 个候选
   └─ 创建异步任务
          ↓ 内部接口或任务队列
       AI Worker
       ├─ 视频动作卡生成
       ├─ 评论聚类
       └─ 推荐排序与理由
```

前端同学只负责让 Demo 使用模拟数据完整运行。前端不直接调用 AI Worker，也不需要理解数据库、模型供应商、prompt 或任务队列。业务后端负责把真实 API 接入前端，并保证接入后页面表现与原 Demo 一致。

### 7.3 AI 后端与业务后端的协作边界

| 场景 | 业务后端提供 | AI 后端返回 | 业务后端最终负责 |
| --- | --- | --- | --- |
| 视频处理 | 来源视频、元信息、任务 ID、输出契约 | 动作卡候选、证据、媒体、置信度、警告 | 校验、版本化、保存、发布和处理状态 |
| 评论聚类 | 标准动作、问题标签、公开评论及来源 ID | 方法分类、摘要、提及数、分歧、风险和原回答 ID | 核验来源、保存聚类、按体感召回和权限控制 |
| 动作推荐 | 当前练单、候选卡、收藏、历史体感和排除项 | 排序后的最多 3 个候选、原因编码、理由和规则版本 | API 返回、事件记录、用户确认后才写入练单 |

AI 后端不直接修改用户练单或训练记录，不自行读取无关个人数据；业务后端不自行改写 AI 生成内容或在缺少来源时补充健身结论。AI 后端把内部调用说明和示例放在 `backend/ai/README.md`，业务后端确认这些输入输出能够接入自己的任务流程。

## 8. 四个人只需要共同确认五件事

下面五件事会直接影响其他人的工作，因此必须一起确认；其他实现细节由对应负责人自行决定。

### 8.1 最终演示走哪条路

四个人按照同一条主流程开发和演示：视频变动作卡 → 加入练单 → 查看推荐 → 开始训练 → 提交体感 → 有问题时查看练友经验 → 完成训练。

### 8.2 四个产品对象分别是什么

所有人必须用同样的含义理解视频动作卡、标准动作、练友经验和练单。尤其不能把其他视频或评论内容写进当前视频动作卡，也不能把后台标准动作当成用户直接训练的卡片。

### 8.3 前端模拟数据长什么样

前端先在 `frontend/mock-data/` 放几份完整示例，例如动作卡、练单、推荐结果、体感和练友经验。业务后端确认这些数据足够实现真实接口，并把接口地址、需要提交的数据和返回示例写进 `docs/api.md`。

`docs/api.md` 由业务后端创建和维护，因为业务后端负责接口和最终接入；前端负责说明页面需要什么，并检查接入后的页面是否正确。字段需要变化时，双方先确认再修改，不让后端接完后前端突然换结构。

### 8.4 固定名称不要各写一套

四个人只需确认会跨模块使用的固定名称：主 Demo 的动作卡和标准动作 ID、肌群编号、五种体感、内容来源标签，以及推荐返回的主要原因。具体数据库字段和 AI 内部状态不需要前端参与决定。

五种体感统一为：

```text
TARGET_FELT          目标部位很有感觉
OTHER_FELT           其他部位更有感觉
NO_CLEAR_FEELING     没找到明显感觉
TOO_DIFFICULT        动作有点吃力
DISCOMFORT           出现不适
```

### 8.5 哪些真实运行，哪些允许预置

主视频生成动作卡、一次推荐排序、练单与训练记录、体感影响下次推荐需要真实运行。抖音入口、其他候选动作卡、历史体感、评论样本和 AI 失败备份允许预置；主 Demo 的视频片段允许人工校准。四个人必须使用同一批固定 Demo 数据。

代码使用短分支和 Pull Request 合并，主分支保持可运行。影响前端模拟数据格式、`docs/api.md`、数据库或部署的修改，需要相关负责人先确认。

## 9. 集成完成的判断标准

四个人的工作不是“各自页面能打开”就算完成，而是以下结果可以在同一环境连续发生：

1. 输入主视频后能看到真实处理进度，并打开一张有来源证据的视频动作卡；
2. 用户可以完全不依赖推荐，手动把动作卡加入练单并开始训练；
3. 推荐最多出现 3 个候选，理由清楚，加入和不感兴趣都由用户主动操作；
4. 训练进度和五类体感能够保存并恢复，普通问题与不适进入不同分支；
5. “没感觉／其他部位更有感觉”能召回相关练友经验，并可查看原评论和原视频；
6. 完成训练后能看到总结，本次体感会影响下一次推荐，但不会改动原练单；
7. AI 或网络失败时有明确降级，不需要现场修改数据库、切后台或替换代码。

功能取舍始终以这条闭环为准。P1 的独立动作知识页、跨视频教学共识、摄像头纠错、组数重量处方等内容，不应挤占 P0 主流程的完成时间。
